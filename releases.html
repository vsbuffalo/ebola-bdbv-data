data/2026-09-04-r0

sitreps 109–113, and flow files state their accumulation window in two columns

Breaking for every consumer of a flow stream. A flow file no longer carries time. It carries window_start and window_stop, the half-open interval [window_start, window_stop) its count accumulated over. Stock files (care_census_*, patients_isolated*, cumul_recovered, uganda_exports) are unchanged and keep time. No file carries both forms.

Migration. window_stop sits where time did and is one day later than it: a row that read 2026-07-13 now reads window_start 2026-07-12, window_stop 2026-07-14. Anything that dates an observation — an axis, a join against the report calendar, a comparison against a data date — wants window_stop minus one day, which is exactly the old time value. In this repository scripts/lib/streams.py does that once for every consumer.

No published count changes. 106 flow files, 4,316 rows: every total, every row and every observation is identical to data/2026-08-30-r6. The conversion is window_start = time - (days_covered - 1), window_stop = time + 1, applied at the single write site in build_streams.py, and all 4,210 interior boundaries tile exactly — no gaps, no overlaps.

What the old form could not say

A row’s window was inferred from the gap to the row before it. Delete an interior row and its neighbour silently widened to cover two days: the model still fit and reported a different answer, with nothing in the file saying so. That is why the omit-and-record convention of registers/window_merged_rows.tsv existed, and why correctness lived in a script and a register rather than in the data.

The first row of every file was worse than silent. It has no predecessor, so its window was not recoverable at all and a consumer inferring from row spacing had to assume one day. Twenty-five of the 106 flow files open on a window wider than that — lab_national on seven days, deaths_national on five — and those first rows now say so for the first time. This is the one place the new form changes what a consumer reads, and it is a correction.

The gate that replaces the row-spacing check

accumulation_windows no longer compares days_covered against row spacing. It checks three things on every flow row, all fatal: positive width, window_stop - window_start == days_covered, and window_start equal to the previous row’s window_stop. days_covered survives as provenance — exactly the window’s width, gated to stay so — and remains the right divisor for a daily rate. n_report_days is not, and never was, a denominator.

Overlaps and gaps are both fatal. Every stream published here covers its span without holes: the flow families that go quiet carry an NA row for the silent day rather than skipping it. A gap appearing means a builder dropped a row.

Two corrections riding along

n_report_days was a constant 1 on the daily companion streams, which is right wherever a widened window came from the source skipping a report — one report day still fed the row — and wrong on the three rows widened by window_merged_rows.tsv, where the source did publish on both days. Those rows (cases_daily_ituri, deaths_daily_ituri, deaths_daily_nord_kivu at 2026-07-13) now read 2. Invisible while the window was inferred; visible the moment the row states it.

registers/stream_families.tsv and the repository README both still described the care streams as carrying a row on every report day, and the README stated the grid was “report days, never calendar days”. Both were superseded when the grid became calendar days; a row now exists on every calendar day a flow family spans. The register text is what meta.json and the generated data dictionary publish, so the stale sentence had been shipping to consumers.

data/2026-08-30-r6

three clamped-zero rows deleted, not carried, so the province filter stops collapsing on 12 July

Breaking for a consumer reading cases_daily_ituri, deaths_daily_ituri or deaths_daily_nord_kivu at daily resolution across 12–13 July 2026. Each file loses its 2026-07-12 row; the 2026-07-13 row is unchanged in value and its days_covered becomes 2. No published total moves.

What was there and why it broke a filter

The source’s own province table went mid-redistribution on 12 July: Ituri’s cumulative cases fell by 39 and deaths by 23, Nord-Kivu’s deaths fell by 1, each a downward revision our carry-forward (carry_forward in build_streams.py, recorded row by row in revisions.tsv) clamps to zero and pays off on the next row that moves upward enough to absorb it. All three deficits close in full on 13 July, so the existing published values were already exactly right: 13 July’s 63 Ituri cases is -39 + 102, its 30 deaths -23 + 53, and Nord-Kivu’s 9 deaths -1 + 10.

The clamped zero itself was the problem, independent of being correct. A zero that isn’t a reported observation still gets scored as one: in a particle filter run against these streams at daily resolution, that single row collapsed the effective sample size from 19,200 particles to 2.2, and pinned the latent trajectory across the date by construction.

Why deletion and not NA

An NA row closes an incidence bin at its own time (docs/camdl-data-spec.md in the modelling repo, “Missing observations: NA is a hole, not a zero”). Marking 12 July NA alone would leave 13 July a one-day window still carrying the two-day total of 63 — the same class of defect, the other direction: a count scored against less flow than it represents instead of more. Deleting the row is the encoding the spec itself names for exactly this case: “the following row’s exposure window silently widens to span the gap” is a caution against deleting when the surviving count does not already cover the gap. Here it does, by construction, because the carry paid the deficit into 13 July before either row was written.

What licenses deleting these three rows and not others

registers/window_merged_rows.tsv is new: a hand-authored register, one row per (stream, column, date) deleted, each justified by the arithmetic above. build_streams.py’s merge_windows reads it and re-verifies every entry against the series it just built — the named row must exist, must not be the first or last row of its stream, and its carried value must be exactly zero — before deleting it and recomputing the following row’s days_covered. A register entry that no longer matches (a re-extraction changes the series under it) stops the build rather than silently deleting the wrong row.

This is deliberately not a general rule the build applies to every clamped zero it finds. revisions.tsv carries two more rows of the identical shape — cases_daily_nord_kivu and deaths_daily_nord_kivu, 2026-06-11, discharged in full by 2026-06-13 — left as a published carried zero because extending this treatment to them has not been decided. The Haut-Uélé deficit spanning 18–22 July is a different shape entirely: it discharges over five rows, two of which are genuine reported zeros, and deleting any one of them would leave a negative count for its neighbour to carry — merge_windows refuses this by construction, since a deleted row must be interior with the deficit fully absorbed by the very next row.

What a consumer should do

A daily-resolution reader of the three affected streams sees a two-day gap in the observation schedule at 12–13 July instead of a zero on 12 July, exactly as days_covered = 2 on the 13 July row already stated before this release — that field was correct throughout; only the row set is now consistent with it. A reader at weekly resolution, or of cases_daily_national / deaths_daily_national / deaths_daily_nord_kivu’s national counterpart, is untouched: none of those files had a clamped row here.

data/2026-08-30-r5

r4 does not rebuild; and the rows we said we published were not reachable

Take this instead of r4. Two defects, both ours, both found by a consumer rather than by our gate.

r4 does not rebuild, and our release gate did not catch it

make streams acquired a dependency on make onset — it reads the reporting delay that onset produces — and nothing in the documented build path supplied it. A consumer running make build streams, which is the documented path, stopped at the guard.

Our own gate passed because it ran make onset in between. That is the whole defect: a gate that exercises an order no consumer uses is not a gate. It is fixed by declaring the dependency (streams: onset) rather than by teaching the gate a special order, and release-check now runs exactly make build && make streams — the same two commands a consumer runs.

The guard itself stays. An empty reporting-delay field reads as “no delay” rather than “not measured”, and that distinction is worth a failed build.

The rows we said we published were in a directory nobody copies

burial_alerts.csv and reporting_delay.csv were written to data/build/series/. A consumer takes data/build/streams/. So the burial-alert rows — asked for specifically so the modelling side could pool and weight them itself rather than trust our pooled figure — were announced as delivered and never arrived.

The layering, stated once so this does not recur:

  • data/build/series/ is internal. Per-report parses carrying statuses, refusal reasons and verbatim quotes, shaped for auditing our extraction against the page. Its shape changes whenever an extractor changes and nothing downstream should pin it.
  • data/build/streams/ is the interface. Stable names, hash-pinned, documented in the generated dictionary.

streams/reference/, new

Row-level tables a consumer pins and hashes but never fits:

reference/burial_alerts.tsv     82 rows   the death-alert ledger, per province-day
reference/reporting_delay.tsv  165 rows   the delay distribution, per onset cohort

meta["reference"] describes each with its row count and columns.

They are deliberately not streams and not in the stream dictionary. A stream is time-indexed, sits on a declared observation grid, and carries a coverage contract in days_covered and n_report_days. A province-day ledger and a delay distribution have none of that, and listing them as streams would make the dictionary’s promises false for two of its entries.

A test now asserts that meta["swab_coverage"] is exactly the pooling of the published burial_alerts.tsv rows, so the summary can never become a number with no rows behind it.

Consumers must add the two paths explicitly — they sit in a subdirectory, so a top-level glob will not find them.

data/2026-08-30-r4

the onset-to-report delay, because the streams and a model’s confirmation event are not the same instant

Not breaking. One field added to meta, one new series file; no stream file changes and no value moves.

The gap this measures

cases_* is indexed by report date. A model’s projected quantity is a confirmation event. Those are different instants and nothing published so far said how far apart. data/build/series/reporting_delay.csv now carries the distribution, per onset-month cohort, and meta["reporting_delay"] the summary.

Pooling it is the one way to get it badly wrong

onset month      n     mean    median   p90    status
2026-04          3    115.0 d    115    117    still arriving
2026-05         87     79.3 d     77    102    still arriving
2026-06        161     39.1 d     37     67    still arriving
2026-07      1,398     10.2 d      9     19    settled
2026-08      1,002      7.1 d      7     13    still arriving

Pooled over everything the mean is 13.2 days. That figure describes no case in particular and overstates the routine delay by roughly a factor of two. The May and June cohorts were not slow to be reported: the epidemic’s early history was reconstructed retrospectively, months after the fact. The routine delay is the July cohort’s — mean 10.2 d, median 9, p90 19.

So no pooled number is published. usable_cohort names the most recent settled cohort, which is July; a cohort is settled when its follow-up has outrun its own 90th percentile. August’s 7.1 d is right-truncated and biased downward — cases with recent onset and a long delay have not been reported yet.

Picking on settledness alone would have returned June, because the early cohorts are settled precisely by being old. Recency is the second discriminator and both are needed.

The long tail is a bigger problem than the shift

Of the cases appearing in each report month — and all of them land in that month’s cases_* bins regardless of when the person fell ill:

              <=14 d    15-30 d    >30 d    >60 d
July           77.7%      16.1%     6.2%     1.8%
August         77.8%      11.9%    10.3%     4.9%

Roughly a tenth of each month’s reported cases had onset more than a month earlier, and that share is growing. This is the same phenomenon as the 22 July harmonisation, which registers/retrospective_batches.tsv records as two named days — but the triangle shows it is continuous rather than confined to the days the source announces. cases_excluding_backlog removes the declared spikes and does not touch this.

How to use it

Convolve with reporting_delay.csv, do not shift by a mean. The distribution is heavily right-skewed — median 9 against a p90 of 19 in the settled cohort — so a single lag parameter fits the centre and misfits both tails.

data/2026-08-30-r3

the safe-burial pillar’s alert ledger, and the swab constants stop living in prose

Not breaking. One field is added to meta; no stream file changes and no value moves. Re-vendor to pin the swab-coverage figures by tag instead of copying them out of a message.

Why this exists

Swab coverage — what fraction of death alerts end in a body actually swabbed — bounds how much of the true mortality the confirmed-death series can see, since a death never swabbed can never become a confirmed case. A model that declares an ascertainment constant is declaring this quantity.

It has been travelling as digits in prose. Figures were derived by an uncommitted ad-hoc analysis, published, corrected once, and then sat in a consumer’s configs at the pre-correction value for three days. No target regenerated them, so nothing could have caught the drift. That is what this release fixes: the numbers are now a build artefact with a rule behind them.

scripts/extract_burial_alerts.py, new

One row per province per report day in data/build/series/burial_alerts.csv — 82 rows across 5 provinces — carrying the pillar’s own counts along the path a death takes:

alerts raised  ->  bodies the team reached  ->  bodies swabbed

plus burials carried out, failures, the report’s own printed percentage, the verbatim sentence, and how the row was licensed. bodies_reached is almost always empty: the reports print that inner step once in 102.

29 of 82 rows are licensed by the document’s own arithmetic — 14 reproduce a printed percentage, 15 satisfy the identity that bodies swabbed plus failures equals alerts raised. The rest publish as unchecked, which is honest rather than silent. Five sentences were refused.

Two readings the extraction had to get right

The carried-over alert count appears in three constructions, and two of them mean the opposite of the third. reports here is from reporter, to postpone — a body not reached that day:

"72 alertes de décès du jour et 23 reports"     -> 72 + 23 = 95
"93 alertes de décès reçues, dont 13 reports"   -> 93 already
"a reçu 37 alertes (15 reports)"                -> 37 already

The parenthetical reads as though it could be either, and the source settles it. 25 August, Nord-Kivu: «le pilier EDS a reçu 37 alertes (15 reports) : 36 corps swabés, un échec de swab» — 36 swabbed plus 1 failure is 37, the stated total, not 37 + 15. The old names also asserted a cadence the data contradicts: a “daily” row covers 2–3 days on 5 of 82, and a “weekly” row 4–8 (the lab stream, 2–9).

2. Every file carries the interval each row covers. New column days_covered: the length in days of (previous row's time, this row's time], the window the count accumulates over. Previously only the daily files stated it — which left it un-stated exactly where row spacing varies most.

3. One name for that column. days_since_prev_report is gone; it is days_covered everywhere.

Also new: n_report_days in every file — how many report days actually contributed to the row. Distinct from days_covered and needed beside it: lab_national.tsv’s first row covers 7 days but rests on 6 reports, and the gap between the two numbers is the coverage a consumer should weigh.

Unchanged on purpose: n_provinces on the lab files and flags on the daily files stay, and stay un-filtered. Publishing the coverage and letting the consumer decide is what let the modelling repo withhold thin rows from scoring while keeping them in the series; pre-filtering would have removed that choice silently.

Exempt: uganda_exports.tsv takes neither new column. Its rows are cumulative importation counts at two bulletin dates — a stock read at a moment, not a count accumulated over a window — so a span column would assert an interval that does not exist. The absence is the signal that this file is a different kind of thing.

Migration: drop the _daily_ infix from column names when reading the daily files; read days_covered instead of days_since_prev_report. Values, row counts and row order are unchanged from -r6.
